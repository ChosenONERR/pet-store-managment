# 宠速星经营助手

这个目录是飞书、本机 Codex 与宠速星经营财务系统之间的确定性执行层。

## 自动任务

营业时段每小时、23:00、23:55 和次日 00:00：

1. 检查已登录 Chrome 的 CDP 连接。
2. 读取当天美团订单。
3. 导出并下载当天商品库存文件。
4. 更新飞书订单、库存和经营驾驶舱。
5. 刷新“每日经营简账”的当月收入、支出页。
6. 校验全部相关公式。
7. 09:00–22:00 每个整点静默同步订单；23:00 先同步当天订单，再私聊提醒逐单配送费、其他支出、补货、干预单和线下成单，并列出系统发现的配送费/成本待补录项；23:55 读取并登记当天推广消费；00:00 验证推广费后完整同步订单与库存并发送 Card 2.0 经营日结。

重点补货条件固定为：`库存 <= 1` 且 `自然月售估算 >= 1`。

`自然月售估算 = 平台月售 - 近30天未取消干预商品数量`，最低按 0 计。当前是估算口径，用来避免干预单把补货优先级虚高。

凌晨日结使用飞书 Card 2.0：顶部显示有效订单、真实单、干预单、线下单和当天赚/亏，补货区使用原生表格展示最紧急 10 款商品。真实单包含平台自然单与线下单，线下单同时单独列示；取消订单不计入有效订单。当天赚/亏按“当天真实单逐单净利润合计－当天支出合计”计算。经营利润与经济利润留在月底复盘。

## 当前对话架构

飞书私聊当前链路为：`店主 → 飞书 → lark_event_bridge.ps1 → 本机 Codex → 只读查询工具/确定性经营脚本 → 飞书回复与表格`。

- 飞书只负责收消息和展示回复，不承担经营判断。
- 本机 Codex 负责理解自然语言、上下文指代、读取本店经营数据、回答问题，并把需要写入的请求转换成白名单结构化动作。系统会显式携带最近对话来理解“这单、昨天、刚才那个”，但每条新消息使用隔离的 Codex 工作会话；旧消息留下的工具结果和待办不会暗中混入当前回答。
- Codex 以只读沙箱运行，不能直接改飞书、美团或本地经营数据。
- 查询订单、干预单、收入、支出、库存、SKU、补货、成本和同步状态时，Codex 会先提出结构化查询请求；外层白名单查询代理调用 `query_business_data.ps1` 读取系统事实并交回 Codex，再由 Codex 回答，不会再要求店主重复提供表格里已有的数据。一次消息最多允许连续 8 轮、累计 30 次只读查询，并会自动停止重复的同参数查询，因此可以先查订单、再查商品、再查 SKU 成本或利润，而不是查询两次就中断。
- 纯查询直接回答，不需要确认；刷新、同步、补发日结等确定性维护动作直接执行；新增或修改经营数据仍先预览、再确认、后事务写入。成本待核对会优先使用 `pending_costs` 精确列出当前 KW/过渡货号、标题、订单数量、SKU 主表行号与当前成本状态，不再用一句“需要继续查询”把已有数据退回给店主。
- 所有新增、修改、覆盖数据的请求仍先发“待确认”；只有店主回复“确认”后，外层确定性脚本才执行并校验公式。
- 如果前一项还没确认，新消息会完整进入待确认队列，不会丢失。系统按先进先出顺序处理；确认或取消当前项后，会自动展示下一项的完整预览。
- 每个预览都会说明准备修改的表、行号或定位键、旧值/新值及联动范围；执行回执只报告实际完成的写入。单纯刷新简账会明确写“没有修改人工录入字段”，不会再显示成“已处理1项”。
- 订单被误登记为干预单时，支持先撤销错误干预记录、再把正确订单登记为干预；同一条确认里的撤销、新增、配送方式和库存状态作为一个原子事务执行，任一步失败都会整体回滚。没有生成可执行动作时不得显示“待确认”。
- 同一飞书消息按消息 ID 幂等；并发消息串行处理，避免两条话互相串入。
- `hermes_chat_bridge.py` 仅作为回滚文件保留，飞书消息已不再转给 Hermes 理解。

本机 Codex 使用当前 Windows 用户已经登录的 Codex CLI，不在项目里保存账号凭据、密钥或 token。

## 旧调度器位置

- Hermes 安装目录：`D:\hermes\hermes-agent`
- 定时执行入口：`%LOCALAPPDATA%\hermes\profiles\viral-video-analyzer\scripts\petstar_periodic_sync.py`、`petstar_input_reminder.py`、`petstar_promotion_expense.py` 和 `petstar_night_sync.py`；订单同步入口共用 `petstar_sync.py`

`D:\hermes\` 是程序安装目录；Hermes 会按当前配置档从 `%LOCALAPPDATA%` 加载技能和定时任务。两处用途不同，不能把技能只放到安装目录。

这些入口暂时只把 Hermes Gateway 当作定时调度器，不调用 Hermes 模型理解对话。当前定时任务：

- `petstar-hourly-sync`：每天 09:00–22:00 每个整点运行，只同步订单且静默
- `petstar-input-reminder`：每天 23:00，提醒逐单配送费、其他支出、补货、干预单和线下成单；补货/干预单/线下单同时提醒调整平台库存
- `petstar-promotion-expense`：每天 23:55，只读美团推广后台，核对后登记当天累计推广消费
- `petstar-night-sync`：每天 00:00，统计刚结束的前一天
- `petstar-night-recovery`：每天 00:20、00:40 检查零点日结；只有零点任务失败或降级时才自动补跑，健康时直接跳过

这些任务均为无模型的确定性脚本任务；需要通知时直接通过飞书 CLI 私聊发送，不消耗模型调用。

## 同步可靠性

- Chrome/CDP、订单读取、库存导出、成本重算、简账刷新、飞书读写和公式校验均使用有限重试；不会无限卡住。
- 库存导出按弹窗语义定位，不依赖“第一个弹窗”；弹窗消失会自动重开，重试期间会复用刚刚已经成功生成的导出任务，避免重复创建。
- 库存导出会等待字段列表结束“正在加载”，并确认商品名称、货号、SKU、库存、月售等必需字段全部出现后才创建任务；字段尚未加载时不会立即误判失败。
- 库存文件先下载为 `.partial`，校验为完整 XLSX 后再覆盖正式文件；下载中断不会破坏上一份可用文件。
- 零点库存导出最终失败时，订单、成本和利润日结仍会继续，卡片会明确标注“库存沿用旧快照”，不会把旧库存伪装成实时数据。
- 每次执行完整追加到 `agent/state/sync_runs.ndjson`，`last_run.json` 只保存最近一次；库存页面失败现场保存在 `agent/state/diagnostics/`，不包含登录凭据。本机的 `agent/state` 是兼容入口，物理数据位于 `D:\PetstarData\state`。
- 每 5 分钟看门狗检查飞书监听和本机 Codex。旧调度器异常只记录风险，不会再让飞书对话一起停止；凌晨发现前一日日结尚未健康完成时，会触发确定性补跑。
- “发现新 KW”、赠品待核对等属于经营提醒，不再把已经成功提交的日结标成运行降级，也不会因此触发 00:20/00:40 重复补跑；只有旧库存回退、写入或校验失败才需要恢复任务。
- 子脚本失败通知会保留实际阶段和错误原因，例如“库存导出字段仍在加载”，不再只显示“子脚本未返回错误详情”。
- 单次同步超过 30 分钟会终止，防止一个卡死进程长期占住后续任务。
- 原子事务执行期间会保留完整写前快照；提交或回滚完成后只保留审计清单和幂等摘要，完整单元格快照不再按小时永久累积。异常中断产生的临时日志会在本次写入结束时清除。
- 大范围回滚按小块恢复并逐块校验，避免单个请求过大；同步启动前解析 `agent/state` 目录联接的真实目标，并同时检查真实状态盘与库存下载盘的剩余空间，任一关键磁盘不足都会在写表前停止。
- 美团订单卡片会先自动展开，再核对卡片标注商品数、商品明细、商品小计和顾客实付；页面结构变化导致明细未加载时，同步会在写表前失败，不会把有收入的订单按 0 商品成本记账。

## 飞书私聊补单登记

`lark_event_bridge.ps1` 直接监听当前已授权飞书 CLI 应用的私聊消息。当前授权用户发送包含“补单”或“干预单”以及 18—20 位订单号的文字后，系统会：

- 对所有会新增、修改或覆盖经营数据的私聊，先发送“待确认”预览，列出明确日期、对象、原值/新值、日期推算及受影响表格；只有回复“确认”才写入。回复“取消”不会改表，直接说“配送费改成8元”等会重新生成预览。
- 查询、解释、“同步支出/刷新简账”和定时同步直接执行，不增加确认步骤。
- “昨天/前天”按原消息时间换算并固化为明确日期；即使第二天才确认，也不会把日期向后漂移。

收到新的私聊文字后，机器人会立即在原消息上显示“正在输入”表情；处理完成或失败后自动撤掉，再发送最终回复。该状态是辅助反馈，添加或撤除失败不会阻断经营数据处理。

- 对一条消息中的多笔订单按订单号逐段解析，分别识别配送方式、配送费和库存恢复状态；订单号始终取用户原文，不交给模型重新生成。
- 新增干预单时若订单号未匹配、但与当天真实订单仅差一位，拒绝写入并提示核对。
- 撤销干预时必须按完整平台订单号同时核对“订单汇总”和“干预订单”；不删除平台订单，也不物理删除飞书行，而是把原记录改成 `WITHDRAWN:原订单号` 的审计标记并把费用归零。所有公式、同步、查询与财务核算只识别纯数字平台订单号，因此撤销标记不会再被计作干预单；同时保留谁在何时撤销了什么，便于追溯。撤销后会重算订单类型、成本、月份收入/支出和当天赚/亏。
- 零点日结前强制核对当天每个干预订单号都存在于订单汇总；有错号或漏匹配时停止日结，避免把干预单计入自然单。日结还必须确认当天 23:55 的推广费抓取成功；抓取失败时停止日结，避免漏扣推广费。

1. 按“今天 / 昨天 / 前天 / 明确日期”识别下单日期。
2. 写入飞书“干预订单”，默认库存状态为“待恢复”。
3. 回复登记结果；重复消息或重复订单不会重复写入。
4. 该订单从每日收入页排除；下一次订单同步补齐商品、平台扣款和配送费，并将干预单商品进货成本按 0 处理。

你可以直接按平时说话的方式表达，例如：“昨天那笔 3402288972032515706 是补单”。示例不是固定格式。

除“确认、取消、修改上一项”外，所有普通私聊都优先交给本机 Codex 理解。飞书仍只有“宠速星经营管家”一个消息入口；桥接层把最近对话显式交给每条消息的隔离 Codex 工作会话来理解省略句，但每条消息仍是唯一的新动作来源，历史动作和旧工具结果不得重放。Codex 只生成白名单动作，外层脚本继续负责校验、待确认预览、幂等和写表。调用过程串行加锁并缓存已处理消息，避免并发串话和事件重投导致重复执行。

`ensure_lark_event_bridge.ps1` 由 Windows 计划任务每 5 分钟运行一次。它不会读取或修改经营数据，只检查飞书事件总线和监听进程；监听器异常退出时会在后台自动拉起。计划任务通过 `run_hidden_watchdog.vbs` 无控制台运行，正常情况下不会弹出 PowerShell 黑框。

系统不会每 5 分钟扫描“干预订单”的人工修改。你改完配送费等内容后，直接对经营管家说“同步一下支出”或“刷新简账”，系统会立即按“干预订单”最新内容重建八月起各月支出并校验公式。

监听器启动以及每次 10 分钟重连时，会并行读取“宠速星经营管家”最近 24 小时私聊，把监听中断期间尚未成功处理的店主文字自动补回。实时监听会立即恢复，不必等待历史补偿结束。系统只保存消息 ID 的哈希和处理状态，不保存聊天正文；业务写入、本机 Codex 调用和飞书回复都继续使用原消息 ID 做幂等，因此同一条消息不会重复登记或重复回复。首次启用只建立现有消息基线，不重放旧对话。

## 飞书私聊配送费

外部配送平台产生的实际费用不会出现在美团订单页。直接把事实告诉经营管家即可，例如：

- “这单我叫闪送送的，花了 13.5 元，订单号是……”
- “这单是干预单，我自己送，没有配送费，订单号是……”

系统会理解整句话：骑手配送会记录实际费用；“自己送/没有配送费”会记录为自配送、0 元。后续美团同步会继续保留平台没有展示、但你已经补录的配送费。

补录配送费同时支持自然单。系统先按订单编号定位，预览 `原配送费 → 新配送费`；确认后更新订单汇总，刷新对应月份收入页、单笔赚/亏和当天赚/亏。人工确认的配送费带有来源标记，后续美团同步不会覆盖。

若旧版数据仍把正数人工配送费只保存在月度收入表、而 `订单汇总` 为 0，简账刷新会在当前全局事务中按完整订单号自动回写该金额和来源标记后继续执行。该自愈只接受能够唯一定位的自然单；订单缺失、重复或已有非零冲突金额时仍停止，且任一步失败会连同当前经营修改一起回滚。

配送费写入成功后，“每日经营简账”的对应月份支出页会自动刷新一行“补单配送费”。“干预订单”的配送方式只保留“自配送”和“骑手配送”两种。

## 飞书私聊线下单

直接自然表达即可，例如：“今天线下卖了 kw1001 两个、kw2054 三个，实收 100 元，自提”。系统会写入“线下订单”，按成交时的 SKU 移动平均成本固化货物成本，再同步到当月收入页。默认当天已到账、自提配送费为 0；赊账或有配送费时按用户明确事实记录。录入后会提醒用户手动调整美团库存。

## 飞书私聊订单赠品

直接说明哪一单加送了什么，例如：“今天美团6号单加送了 kw4189 1个作为赠品”或“订单号……赠送 kw1001×2”。系统会在隐藏的“赠品记录”冻结登记时单位成本，并在收入页“赠品（KW）”显示货号与数量。

订单还没同步进飞书时也可以立即登记，但必须提供完整平台订单编号。确认后系统先显示“待同步”，冻结赠品货号、数量和当时成本；下一次订单同步会自动匹配“美团几号单”。待匹配期间不计入利润、不扣减成本账库存；超过24小时仍找不到订单、匹配不唯一或订单已取消时，飞书会提醒核对。

- 自然单和线下单：赠品成本并入本单“货物成本”，会降低本单与当天利润。
- 干预单：购买商品成本仍按 0；真实赠品成本进入当月支出页“营销赠品支出”。
- 赠品会扣减 `SKU成本主表` 的成本账数量，但系统不会修改美团库存，因此回执会提醒手动扣减平台库存。
- SKU 成本缺失时，备注明确写“赠品成本待核对：kw…未知成本价”，相关利润暂不显示；零成本试吃装仍记录数量、成本为 0。

## 每日经营简账

- 收入页只保留自然、未取消订单，不包含干预单。
- 收入页固定按“日期 → 平台 → 平台内当日单号数字”排序；平台顺序为美团、饿了么、京东到家、淘宝闪购、线下、其他。
- 单笔赚/亏 = 扣佣后收入 - 货物成本（含赠品）- 配送费。
- 自然单商品成本尚未核对时，单笔赚/亏和对应当天赚/亏留空，不把未知成本按 0 元虚增利润。
- 当天赚/亏只在当天最后一笔自然单所在行显示，便于一眼看完当天结果。
- 售出货品优先显示当前 `kw` 货号和数量；旧 `csx` 能映射时显示 `kw`，无法映射时直接保留原货号，不影响独立匹配参考成本。
- 支出页允许用户自由填写日期、项目、费用和备注。普通手填行会保留；系统管理的补单行按订单号和项目稳定更新。
- 每个干预订单固定生成“补单平台扣款”和“补单配送费”两行；识别不到配送费时写 0 并标记“待补录”，用户手工补录后后续同步保留该金额。干预单不计购买商品进货成本；存在赠品时再生成“营销赠品支出”。

## 动态商品成本

- `SKU成本主表` 以美团 `sku_id` 作为稳定商品身份，保存当前 KW、当前 CSX/过渡码、采购包装换算数、基准单位成本、当前移动平均成本和成本账数量。对话内部执行成本修正时优先使用 `sku_id` 唯一定位；即使过渡货号在历史行和当前行重复，也不会误改或因歧义丢失已经查到的当前商品。
- 每次完整库存同步按 `sku_id` 更新上架商品、当前 KW、规格和库存。新身份自动建档并标记“缺少成本”，已有人工成本不会被覆盖。
- KW 是可调整、可复用的当前货号，不是永久商品身份；旧 KW 不保存为历史别名。历史订单保存成交时 `sku_id` 与成本快照。
- 同一当前 KW 若对应多个不同 `sku_id`，相关行标记为“当前KW冲突待核对”，系统不会自动合并或猜测归属。
- `补货记录` 的“采购包装数量”表示买了几箱/几包；系统自动换算“入库销售单位数量”。普通补货只写入补货记录，并局部更新该 SKU 的当前移动平均成本和成本账数量，不会自动刷新历史订单、收入、利润、每日经营简账、月份收入/支出或现金流。
- 明确说“试吃装、赠送、免费、成本为0”时允许零成本入库。新 KW 尚未同步到 `SKU成本主表` 时，确认后先建立待平台同步档案；以后库存同步补齐商品标题、商品 ID、销售状态和规格，不覆盖本次补货形成的成本记录。
- 移动平均成本 =（补货前库存成本 + 本次实际采购金额）÷ 补货后销售单位数量。
- 自然单在成交时固化商品 ID 和单位成本快照；以后改 KW、登记补货或单独修改 SKU 当前成本，都不会倒改历史订单利润。只有店主明确指定某个历史订单并要求修正该单成本时，系统才修改该订单并刷新其所属月份，不做全量历史重算。
- 定时同步重新排序订单行时，单位成本、货物成本和利润快照会随对应订单商品一起移动；只为本次新增的订单商品初始化成本。旧订单原本成本为空时仍保持“待确认”，不会因为后来补货或修改 SKU 当前成本而自动补算。
- 成本初始化从 2026-09-08 起采用移动平均。此前订单使用经过包装单位审计的基准单位成本。
- 成本只使用 `SKU成本主表` 中已有明确数值的移动平均成本。主表成本为空时，相关订单/赠品标记“成本待核对”，该单利润和当天利润留空；旧“商品成本”表只供人工核对，不再静默回填利润。
- KW 可以在商品移走后重新分配，但同一时刻必须唯一。改号后下一次库存同步按 `sku_id` 认回商品，不靠旧 KW 猜历史。
- `SKU成本主表`允许过渡期 KW 为空：没有 KW 时把当前 CSX/过渡货号放在 B 列，长期日常操作仍优先使用 KW。
- 可以直接自然地说“把 kw1109 的销售单位成本改成 0 元”或“csx104 每罐成本应为 1.25 元”。系统会先给出 `SKU成本主表` 的准确行号、旧成本、新成本，并明确说明默认只改主表；确认后才写入并回读校验。只有同时明确给出历史订单号并要求修正该单时，才会显示并执行该订单及所属月份的联动。这里填写的是每个销售单位的成本，整箱金额必须先按箱内销售单位数换算。

### 通过飞书修改 KW 货号

可以自然地说“把 kw1003 改成 kw1203”或“我将 kw1003 修改为 kw1203”。系统会先检查两个号码：

- 新 KW 未被占用：更新 `SKU成本主表` 的当前 KW，不保留旧 KW 别名；历史订单依靠商品 ID 与成交成本快照保持不变。也支持“csx194 的 KW 登记为 kw2093”这类从过渡货号绑定当前 KW 的表达。店主通过对话确认的当前 KW 会被标记为人工确认，后续库存同步不会被平台旧货号覆盖。
- 新 KW 已被另一件商品占用：默认不修改，直接列出冲突的两件商品。只有店主明确确认旧商品已经下架、该 KW 要转给新商品时，系统才解除旧商品当前 KW 并完成接管。
- 相同改号消息重复到达：只回报已经完成，不重复写入。

改号只维护飞书当前映射，不会修改美团商品后台。美团端货号由店主修改后，下一次库存同步会按 `sku_id` 读取并更新当前 KW。

## 库存批次、生产日期与到期日期

- `SKU成本主表` 的“最早过期日期”记录该 SKU 当前库存中最早到期的一批；非食品、没有有效期的商品可以留空或标记为“-”。
- 可以直接私聊经营管家，例如：“kw1055 的最早过期是 2027年3月18日”。再次提供同一货号的新日期会覆盖旧日期。
- 过渡期也支持 CSX，例如：“csx364 最早到期是 2027-03-18”；系统会通过成本主表映射到对应行。
- 可以说“kw1055 没有过期日期”或“清空 kw1055 的过期日期”，系统会将该字段标记为无。
- `库存批次` 隐藏表只在店主明确要求维护批次日期时保存商品 ID、生产日期、保质期和推算到期日；普通补货不会顺带修改该表。
- 可以说“kw1055 生产日期是 2026年8月1日，保质期18个月”，系统按日历推算到期日期。只给生产日期时会追问保质期，不会猜测。
- 若同一次补货同时提供生产日期和保质期，这些日期只保存在该条补货记录中；需要同步维护隐藏库存批次时，店主另行明确提出。
- 每天 00:00 的经营日结会列出“临期商品”：当前库存最早到期日期不晚于日结日期加 8 个自然月，且当前库存仍大于 0 的商品。已经过期的商品也会提醒，并优先排在前面。
- 临期提醒展示货号、商品标题、当前库存、到期日期和剩余天数；卡片最多展示 10 个，其余在 `SKU成本主表` 查看。没有填写到期日期的商品不会被系统猜测或提醒。

## 可以自然交代给本机 Codex 的日常事情

- `登记干预单 订单号 备注`
- `订单号 库存已经恢复`
- `今天补货 kw1082 2箱，采购金额 100 元，今天已付款 100 元`
- `今天其他现金支出 30 元，配送`
- `今天经营费用 50 元，包装耗材`
- `今天老板取款 200 元`
- `本月美团实际到账 5000 元`
- `今天线下卖了 kw1001×2，收了 80 元，顾客自提`

这些只是表达示例，不是命令模板。本机 Codex 会先理解自然语言和上下文，再转换成结构化参数；外层监听器给出预览，你确认后才调用 `record_finance_event.ps1`。只有关键金额、订单号或付款事实确实缺失时才会用自然语言追问。

执行层会把常见自然说法归一为账表使用的标准值，例如“当天到账”按“已到账”处理，“京东外卖”按“京东到家”平台处理。此类同义表达不会再因为 CLI 枚举不同而被误报为理解失败。

也可以直接问经营问题，例如“从开业至今有多少笔干预单、花了多少钱”“昨天哪些订单配送费还是空的”“kw1104现在成本和库存是多少”“最近一次同步是否成功”。这些问题由 Codex 实时读取系统数据后回答，不要求固定问法。

## Agent 输入与输出

当前输入有三类：

1. 飞书私聊文字：登记干预单、补录配送费、确认库存已恢复、记录线下单、补货/付款、经营费用、现金支出、老板取款、平台到账和月度参数。
2. 已登录 Chrome：定时读取美团订单页并创建库存导出；不接收也不保存登录凭据。
3. 本地与飞书基础数据：商品成本、KW/CSX 映射、干预订单、补货记录和月度补充数据。

当前输出有四类：

1. 飞书即时回执：说明写入了什么、金额/订单号、是否重复以及下一步需要做什么。
2. 每日经营简账：自然单逐单收入、商品成本、配送费、单笔赚/亏、当天赚/亏；干预单平台扣款和配送费进入支出页。
3. 每天 09:00–22:00 每小时静默同步；23:00 先同步再私聊五项录入检查和系统待确认项；23:55 只读美团推广后台并登记当天累计推广消费；次日 00:00 只有在推广费抓取成功后才发送 Card 2.0 日结：有效订单、干预单、真实单、线下单、推广费、当天暂估赚/亏、待核对警告、紧急补货表格和未来 8 个自然月内的临期商品表格。试吃装、尝鲜装、试吃尝鲜、试用装和体验装不进入补货提醒。
4. 失败通知：Chrome、登录、页面结构、下载字段、飞书授权或公式校验失败时明确报错，不静默跳过。

## 飞书授权稳定性

- 定时同步固定调用当前 Windows 用户 npm 目录中的同一份 `lark-cli.cmd`，不依赖 Hermes 子进程的 PATH 顺序。
- 飞书 CLI 请求不继承 Hermes Gateway 的本地 HTTP 代理；美团网页自动化仍按 web-access 的代理与 Chrome CDP 规则运行。
- 预检先执行服务端授权验证，再对驾驶舱 `A1:A1` 发起最小只读请求。只读请求成功即认定飞书可用，避免本地状态刷新瞬间被误判为“授权未就绪”。
- 预检最多阶梯重试 5 次；失败记录仅保存用户状态、凭据状态、到期时间和只读探针错误，不保存 token、cookie 或密钥。
- 系统只缓存当前通知收件人的 `open_id` 与应用 ID。即使用户凭据暂时不可读，机器人身份仍可把失败卡片发给同一位店主。
- 只有刷新凭据确实过期或缺失时才要求重新授权；普通瞬时错误交由下一次重试或整点同步自动恢复。
- 飞书自然语言层使用常驻 Codex app-server；每次消息和看门狗检查都会比对受保护凭据文件的代次。桌面端切换 Codex 登录账户后，系统会自动重启内部 app-server 并继续使用新账户，不需要手动重启飞书监听器。
- 本机已将美团自动化固定绑定到 Chrome `Default` 资料（界面名称“人员 1”），绑定记录保存在 D 盘运行状态中，不保存 Cookie、密码或令牌。订单、库存和推广费只会使用该资料，不再枚举其他 Chrome 账户；该资料登录失效时直接失败并只提醒一次。

当前不能自动完成的事项：修改美团库存、替用户评价/退款/取消订单、猜测平台没有展示的配送费、自动确认一笔采购是否已经付款。未展示的配送费和付款事实必须由用户提供。

## 每日推广费

- 每天 23:55 从当前已登录的美团推广后台读取当天累计消费；系统只读页面，不保存登录参数、Cookie 或推广后台 URL 中的临时标识。
- 同时核对推广账户首页累计消费与资金流水“推广消费”。两处金额不一致时不写账，并发送明确失败提醒。
- 23:55 抓取失败只保存失败状态；00:00 日结统一发送一次明确失败卡片。00:20/00:40 对相同原因重试时使用稳定幂等键，不再重复推送相同报错。
- 次日 03:00 前允许补抓前一天已经结算的唯一“推广消费”行；此时首页“今日累计”已清零，系统改为严格按日期和类型读取资金流水，不会把次日的 0 元倒记为前一天费用。
- 飞书支出项目固定为“投流推广费”。同一天重复运行按日期更新同一行及月度结算差额，不会重复累计。
- 23:55 取得的是当天接近结束时的累计消费。店主手动开启和关闭推广的使用方式下，该金额直接用于 00:00 日结；抓取失败时日结停止，不会把漏扣推广费的利润发出来。

“干预订单”表中，“订单编号”是唯一识别键，“单号”显示美团当天的第几号单。同步会自动补齐日期、只含货号和数量的购买内容、补单金额、平台费用、能够识别的配送费和单号；平台未展示的配送费由飞书私聊补录并永久保留。总成本公式等于平台费用加配送费，干预单商品进货成本固定为 0。“补单人”是自由填写字段；“是否已恢复库存”“是否已好评”和备注按实际情况填写。

商品成本按美团 SKU ID 优先定位 `SKU成本主表`，再使用当前 `kw`/`csx` 做唯一匹配；只有主表存在明确成本数值时才计入。无法唯一定位或主表成本为空时留在待核对清单，不使用旧“商品成本”参考值猜成本。

```powershell
python .\agent\petstar_cli.py sync --skip-sync --dry-run
```

## 数据边界

- 美团自动化永远只读订单、创建库存导出和下载文件。
- 不自动改美团库存；只提醒需要恢复的货号和数量。
- 老板取款只进现金流，不进经营费用。
- 市场租金机会成本只影响经济利润，不影响经营利润或现金流。
