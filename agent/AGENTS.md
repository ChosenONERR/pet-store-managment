# 宠速星本机 Codex Agent

## 目标

把美团订单、库存、飞书经营驾驶舱和日常基础录入连接成低打扰的经营助手。

## 文件约定

- `run_sync_and_notify.ps1`：只读同步美团数据、校验飞书公式、生成经营摘要并发送飞书通知。
- `run_scheduled_job.ps1`：仓库内统一的定时任务入口；根据任务类型计算日期和参数，不依赖 Hermes 配置目录中的脚本副本。
- `run_hidden_scheduled_job.vbs`：Windows 计划任务的无控制台包装器。
- `configure_petstar_scheduled_tasks.ps1`：在新电脑显式注册整点、提醒、推广费、日结、每周审计和补偿任务；这是系统配置脚本，不得在未确认时自动执行。
- `run_weekly_maintenance.ps1`：每周一 00:00（周日晚结束后）先做全历史只读审计；只有审计失败才调用原子化全量重建，审计健康时零写入。
- `sync_promotion_expense.ps1`：每天 23:55 只读美团推广后台的当日累计消费，交叉核对账户首页与资金流水后，以“日期 + 投流推广费”为唯一键写入当月支出和月度结算；同日重跑只更新原记录，不重复追加。
- `record_finance_event.ps1`：把经用户确认的结构化经营事件写入现有飞书表。
- `record_finance_event.ps1` 维护商品当前货号、普通补货记录和当前 SKU 成本；只有店主明确要求维护库存批次时，才处理生产日期/保质期/到期日期。订单赠品按登记时成本快照写入隐藏的 `赠品记录`；只接受明确的商品、数量与订单，不推测。
- `reconcile_pending_gifts.ps1`：订单尚未同步时允许按完整订单编号暂存赠品；后续同步自动补齐平台、日期和当天单号。超过 24 小时未匹配、匹配不唯一或订单已取消时返回告警。
- `sync_daily_ledger.ps1`：把经营驾驶舱的自然单和干预费用刷新到“每日经营简账”，保留用户手填备注与支出。
- `sync_new_skus.ps1`：以美团 `sku_id` 为商品身份合并库存资料；同一商品更新当前 KW/CSX，同一 KW 改绑到另一商品时不得继承旧商品成本。
- `codex_chat_bridge.py`：把飞书普通私聊交给串行的本机 Codex。Codex 是经营管家的唯一自然语言决策层：每条店主消息创建隔离工作会话，并显式注入最近对话；只在该消息内部延续会话、连续选择只读经营工具，直到证据充分后再回答或生成白名单动作。不同店主消息不得复用隐藏模型会话，避免旧工具结果或旧待办污染当前请求；外层只负责执行工具、校验结果和落实确认后的事务，不用关键词替代模型理解。
- `query_business_data.ps1`：外层工具代理专用的只读经营查询入口；按数据集读取经营概览、订单汇总、订单商品、待核成本、干预单、SKU、库存、补货、月份收入/支出、经营利润和最近同步状态，支持日期、订单号、货号与关键词过滤，只输出脱敏 JSON，禁止任何写入。Codex 沙箱不直接启动该脚本。
- `codex_response_schema.json`：本机 Codex 与确定性执行层之间的结构化动作契约。
- `hermes_chat_bridge.py`：只作为回滚文件保留，不得再由飞书入站监听器调用。
- `lark_event_bridge.ps1`：飞书唯一入站监听器；除“确认/取消/调整上一项”外，所有普通自然语言必须先交给本机 Codex 理解，再由确定性执行层校验和执行。旧关键词路由仅作为关闭状态的回滚实现，不得抢先解释业务意图。
- 飞书私聊中的经营数据新增、修改和覆盖实行两阶段确认：先生成含明确日期、原值/新值、推算结果和受影响表格的待确认预览，用户回复“确认”后才调用 `record_finance_event.ps1`；“取消”不得写入，补充/改正内容后必须重新预览。
- 查询、解释、手动刷新简账和系统定时同步不进入确认流程；它们不得借机修改用户手填经营事实。
- `state/pending_confirmations.json` 保存当前用户尚未完成的结构化待确认队列和必要原文，最长保留 48 小时，不保存密钥、token、Cookie 或飞书授权信息；新请求不得因前一项未确认而丢弃，按先进先出顺序逐项确认。
- 多订单干预消息必须按原文订单号逐段确定性解析，不允许由模型重写订单号；日结前必须通过“干预订单号 ↔ 当日订单汇总”一致性门禁。
- `ensure_lark_event_bridge.ps1`：五分钟运行看门狗；检查事件总线、监听进程及当前 Chrome/CDP 实例。监听器或 CDP 代理异常退出时后台拉起；新 Chrome 实例只主动触发一次 Allow，授权恢复后自动补跑一次同步。看门狗本身不得读取或改写经营表。
- `run_hidden_watchdog.vbs`：Windows 计划任务的无控制台启动器；看门狗必须通过该入口后台运行，禁止直接以前台 `powershell.exe` 动作造成弹窗。
- `ensure_lark_event_bridge.ps1` 检查飞书事件总线、监听进程与本机 Codex；Hermes Gateway 仅暂时承载旧的无模型定时调度，其异常不得再阻断飞书对话。凌晨补偿仍直接调用确定性日结脚本。
- `README.md`：用户可见的使用方法、命令示例和边界。
- `state/`：运行时状态的兼容入口；本机通过目录联接指向 `D:\PetstarData\state`，保存幂等事件和最近执行结果；不得保存任何授权凭据。
- `state/sync_runs.ndjson`：同步运行历史；`state/diagnostics/`：页面故障现场截图与非敏感状态摘要。

## 边界

- 配送费同步每小时复查目标日全部有效美团自然单，0元/未发配送不代表已结算；跨天待查约单继续追踪，直到明确完成、人工确认自配送、取消或变为干预单。只读麦芽田/青云聚信，绝不发单、取消、加小费或付款。按完整平台订单号匹配，人工费用优先；缺失、冲突或证据不足只告警，不填0或覆盖人工事实。费用变化只刷新对应订单与月份，不触发商品成本重建。
- 经营毛利只扣商品/赠品成本及首次配送费；经营利润以月份支出表为唯一经营费用来源，月度结算 G、N:R 为自动派生汇总，不得另扣干预订单总成本。未知费用必须显示利润暂估，采购付款和老板取款不得混入经营费用。
- 售后追加配送费以 OperatingExpense 新增到支出表并关联订单号，不得替换首次配送费。普通费用录入和简账更新仅刷新对应月份费用汇总，禁止借此重算历史订单成本。

- 不在脚本内保存群 ID、密钥、token 或浏览器 Cookie。通知兜底只允许在 `state/` 缓存当前收件人的 open_id 和应用 ID，不得缓存凭据。
- 不修改美团订单、评价、退款、商品、价格或库存。
- 干预单造成的库存扣减只生成恢复提醒；只有用户明确说已恢复后，才更新飞书处理状态。
- 采购入库和采购付款分别记录，不因为日期相同就混为一项。
- 所有飞书写入后都要校验相关公式，并回读关键结果。
- “每日经营简账”收入页只允许自然、未取消订单；自然/线下单赠品成本并入货物成本。干预单不计购买商品进货成本，但实际赠品成本单列为“营销赠品支出”。
- 赠品登记时冻结单位成本；订单尚未同步时先标记“待同步”，不得提前计入利润或扣减成本账库存。匹配到有效订单后才扣减；后续补货价格变化不得倒改历史赠品成本。平台库存仍只提醒用户手动调整。
- 用户可用自然语言表达，不要求固定命令格式；“自己送/自配送/没有配送费”视为已确认配送费为 0 元。只有关键事实确实缺失时才自然追问。
- “今天/昨天/前天”以消息创建时间和 Asia/Shanghai 时区换算；预览必须显示实际 `yyyy-MM-dd` 日期。历史干预单、自然单配送费等修改以平台订单号作为唯一键，并联动重算对应日期和月份。
- 自然单人工补录的配送费是人工确认值，写入 `订单汇总` 后必须带来源标记；后续美团同步不得用缺失值或平台旧值覆盖，收入页与当天赚/亏随简账刷新重算。
- 美团 `sku_id` 是商品的稳定身份；KW 是当前店内货号/货架位置，可以改绑和复用，不能作为永久商品身份，也不得把旧 KW 保存成历史别名。
- “把 kw… 改成 kw…”表示给同一商品调整当前 KW。若新 KW 已被另一件商品占用，只有用户明确说明该商品已下架/移走/替换时才允许解除原绑定；任何改绑都不得倒改历史订单的商品与成本快照。
- CSX 只作为过渡货号/货架码参与当前匹配，不承载历史 KW 别名。
- 用户直接说“同步一下支出/刷新简账”时立即重建八月起的月份支出；不轮询 `干预订单` 的人工修改。
- 普通补货只新增 `补货记录` 并局部更新该 SKU 在 `SKU成本主表` 中的当前移动平均成本与成本账数量；不得自动重算历史订单、收入、利润、每日经营简账、月份收入/支出、现金流或驾驶舱，也不得写入其他经营表。补货消息带生产日期和保质期时，只把这些事实保存在该条补货记录中；除非店主另行明确要求维护库存批次，否则不得扩展写入。
- 明确属于试吃装、赠送或免费取得的补货允许采购金额为 0；新 KW 尚未出现在主表时先建立“待平台同步”档案，后续库存同步只补全商品标题、商品 ID、销售状态和规格，不覆盖已经形成的成本账。
- “补货”同时覆盖既有 SKU 补库和新品首次入库，不要要求店主改用固定指令。提供 KW+CSX 时应以两者联合校验：CSX 能在主表唯一定位且 KW 未被其他商品占用时，直接绑定当前 KW 并记录补货；任一编码重复或分别指向不同行时停止写入并说明冲突行。
- 店主可通过自然语言纠正某个 KW/CSX 的销售单位成本。默认只更新 `SKU成本主表` 的基准单位成本、当前成本与核对状态，不得自动重算任何历史订单或报表。只有店主明确指定某个历史订单，并明确要求更新该单成本或利润时，才允许修改该订单中对应 SKU 的成本并刷新该订单所属月份；不得扩大为全量历史重算。确认预览必须明确写出“只改主表”或具体联动订单号。
- 定时订单同步必须按订单号、稳定商品 ID（缺失时用货号、标题和规格）携带已有单位成本、货物成本和利润快照，禁止因行排序变化造成成本串行。成本重建只允许为本次真正新增的订单商品初始化快照；已有历史行即使成本为空，也继续保持待确认，直到店主明确指定历史订单要求修正。
- 订单和赠品成本只允许使用 `SKU成本主表` 中已有明确数值的成本，或已冻结且无法再定位稳定商品身份的历史订单快照。主表成本为空时，必须标记成本待核对并暂停该单利润；旧“商品成本”表只能供人工参考，禁止静默兜底入账。
- 若订单商品尚无可唯一使用的 KW/CSX，但 `pending_costs` 已通过美团 SKU ID 唯一定位到 `SKU成本主表`，成本确认动作必须使用内部 `sku_id:<美团SKU ID>` 稳定引用；回复仍展示当前 KW 或过渡货号。执行层必须按商品 ID 再次验证唯一行，禁止拿重复过渡号取第一行，也禁止按标题模糊写入。
- 待确认预览不得只有标题，必须逐项说明表名、定位方式或行号、旧值/新值和联动影响；执行回执只能陈述已经成功写入或刷新的内容，维护动作不得冒充经营数据修改。
- 每天 00:00 日结必须提醒当前库存中不晚于日结日期加 8 个自然月到期的商品；已过期商品优先，库存为 0 的商品不提醒，未登记到期日期时不得猜测。
- 每天 00:00 日结优先确认当天 23:55 的推广费抓取成功（0 元也要有成功状态）；若美团流水尚未结算或 Chrome 暂不可用，订单、成本和受影响月份仍继续核对，但日结必须明确标记为“推广费待补、净利润非最终值”，并由后续恢复任务自动补抓，禁止把未知推广费按 0 元当成最终结果。
- 每天 00:00 日结必须全量复核有效干预单：按完整订单号核对订单汇总、订单商品、平台扣款和月份支出。可由已有平台数据确定的缺失项自动补齐；仍缺失或冲突的订单必须在飞书日结中列出，未知平台扣款不得按 0 元入账。
- 每天 10:00 的引流款运营建议只能从最新库存快照中选择“售卖中且库存大于 0”的商品；近期自然销量只能作参考，不能作为是否推荐的硬门槛。建议仅限标题、主图、折扣价、库存和平台推广状态等正常运营检查，禁止自动创建交易、评价或修改美团商品/库存。
- 10点运营提醒的搜索词以飞书“关键词库”为唯一来源；新增/停用下一次读取生效，不以本地固定词覆盖人工维护。关键词必须与推荐商品品类/品牌或明确关联货号对应；无法匹配时只提醒完善关联，不猜商品。初始化脚本只给空表填种子，不删除或覆盖既有人工词库。
- 驾驶舱历史月份选择只改变月度经营指标和该月订单成本待核对数；库存、缺货/低库存和同步状态保持当前值。系统通知必须读取独立的当前月指标，禁止受用户停留的历史月份影响。
- 退款、干预单、赠品和普通订单变化只能刷新相关订单及其所属月份；缺少变更范围证据时停止写入并通知。除每周全历史审计失败或店主明确要求外，禁止自动运行全量成本重建和全月简账刷新。
- 已确认的新增/撤销干预单、指定订单实际履约和退款处置必须把完整订单号传给成本脚本的增量模式；只写该订单、实际涉及的 SKU 行和所属月份。禁止因为单笔经营事件重写 `SKU成本主表` 整列。
- 线上订单私下加购时，若原订单商品及数量全部保留、仅新增一个商品且店主明确最终收入或额外付款，可将“最终收入－原商家收入”作为该新增商品成交额；多个新增/替换商品或原商品数量变化时不得猜测金额分摊。用户未提配送时必须在确认执行时沿用订单当前配送费，不能用预览前查询到的旧值覆盖。该动作只覆盖指定订单并刷新所属月份，不修改美团订单或库存。
- 推广费子步骤失败只写结构化状态，由日结统一发送一次失败通知；同一日期、模式和失败原因必须使用稳定幂等键。次日 03:00 前允许按日期唯一定位资金流水中的前一天“推广消费”进行补抓，禁止把已清零的次日累计倒记为前一天费用。
- 入站监听启动及每次重连时，必须并行补偿最近 24 小时内未成功处理的店主私聊；使用飞书消息 ID 的哈希写入 `state/handled_inbound_messages.ndjson`，禁止重复登记或重复回复。
- 每条符合条件的店主私聊最终必须得到一次成功、追问或失败回执；单条消息异常不得终止监听器，回复发送失败时不得把该消息标记为已完成，并由补偿机制重试。
- 本机 Codex 只在 `read-only` 沙箱中理解消息，不直接启动 PowerShell 或飞书 CLI。需要真实经营数据时输出白名单查询请求，`codex_chat_bridge.py` 校验参数后调用 `query_business_data.ps1`，再把查询结果交回 Codex；结构化写入动作必须回到 `lark_event_bridge.ps1` 做白名单校验、预览和确认执行。
- 飞书只是消息入口与结果展示层。任何可由现有经营数据回答的问题，都应由 Codex 主动查询后回答，不得反向要求店主提供系统已经保存的表格明细或汇总数。查询失败时要说明具体失败的数据集并给出可执行恢复动作，禁止用“我看不到表格”作为泛化回复。
- Codex 工具循环最多允许 8 轮、每轮最多 6 个只读查询；不能用固定两轮截断正常分析。同一组查询参数重复出现时立即停止重复调用，并把已经取得的证据交回 Codex说明缺口，禁止无限循环。
- 精确订单问题优先使用 `order_items`；成本缺失、成本确认和订单利润修正优先使用 `pending_costs`；时间范围盈利问题优先使用 `profit`。这些工具必须返回订单号、日期、当前 KW/CSX、商品标题、数量、成本状态和必要的 SKU 主表定位信息，不能只给汇总数。
- 每一轮工具结果都属于当前消息上下文，并必须同时重申当前事件键与店主原话，明确只以当前事件的工具证据为准；Codex 必须基于结果继续决策，不能要求店主重复提供系统已经保存的事实。只有工具返回确实不存在或冲突时，才追问一个最关键事实。
- 普通查询不进入确认队列；同步/刷新等已有只读或可重建维护动作直接执行；新增、修改、覆盖经营事实仍实行预览确认。一次消息含查询与修改时，先回答已确认的查询结果，再给出待确认修改，不得丢弃其中任一事项。
- 多条飞书消息调用本机 Codex 时必须串行持锁；相同消息 ID 和阶段必须读取幂等缓存，避免并发串话和重复执行。
- 所有读写 `SKU成本主表` 的运行脚本必须先通过 `sku_master_schema.ps1` 按中文表头解析列位置；禁止硬编码成本、库存、日期、商品 ID 等业务列号。表头缺失、重复或改名时必须在写入前失败，不得猜测列位置。
- Python 或计划任务调用 PowerShell 入口时必须使用 `powershell.exe -File <真实路径>`；不得把入口文件读入 `ScriptBlock::Create`，否则 `$PSScriptRoot` 会丢失并破坏相对依赖。
- 所有经营数据写入必须进入同一个全局串行事务通道；禁止飞书对话、定时同步和手工维护脚本并发改写经营表。
- 同一条已确认请求中的多个动作是一个原子经营事务：写前保存受影响单元格的值、公式和样式，全部写入、衍生表重算和校验通过后才提交；任一步失败必须逆序回滚。
- 事务状态必须明确区分 `active`、`committed`、`rolled_back`、`rollback_pending`；未确认提交不得写入“已处理”幂等日志，回执发送失败不得倒改已提交经营数据。
- 事务回滚失败时禁止继续新的经营写入；必须先自动重试未完成回滚，并用事务号报告明确的人工处理项。
- 完整单元格写前快照只允许存在于 `active` 和 `rollback_pending` 事务；事务提交或成功回滚后必须立即压缩为范围清单、条目数量和幂等事件摘要，不得永久保留大体积 `cells` 数据。
- 事务日志采用同目录临时文件原子替换；无论写入成功或失败，都必须清除本次产生的临时文件。回滚大范围时必须分块写回，避免单个飞书请求过大导致恢复失败。
- 同步前置检查必须解析运行状态目录联接的真实目标，并同时检查真实状态盘和库存下载盘；状态盘空间不足时必须在任何飞书经营写入前停止。
- 美团订单卡片必须先展开并确认商品行数量达到卡片标注的“x件商品”后才能解析；有预计收入却没有商品明细、商品小计或顾客实付的订单属于不完整提取，必须在写入飞书前整批失败，禁止按 0 成本入账。
- 库存导出弹窗出现后，必须等待“正在加载”结束且全部必需字段复选框实际出现，再选择字段并创建导出；弹窗可见不等于字段已就绪。
- 日结 `degraded` 只表示使用旧库存等运行层降级，不得把“发现新 KW”、赠品待核对等经营提醒标成运行失败或触发重复补跑。经营提醒继续展示，但健康日结只按写入、校验和数据源是否降级判断。
- 子脚本失败必须向上层返回可解析的具体错误和阶段；失败卡片不得用“子脚本未返回错误详情”掩盖已经捕获的页面诊断。
- Codex 结构化动作进入执行层前必须归一化自然语言枚举值；例如“当天到账”归一为“已到账”，“京东外卖”归一为“京东到家”，不得让 CLI 参数校验错误冒充理解失败。
